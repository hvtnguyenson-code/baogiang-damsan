# ADR-007 — Authentication session, cookie and CSRF policy

## Status

Accepted for `PHASE-01-AUTH-SESSION-RUNTIME-001`.

## Decision

Authentication uses an opaque 256-bit token generated by `crypto.randomBytes`. The raw token exists only in the client cookie; PostgreSQL stores only its SHA-256 digest. Sessions are server-side, expire after a configured TTL, may be revoked, and update `lastSeenAt` no more often than a configured interval.

The cookie is `HttpOnly`, `SameSite=Lax`, scoped to `/api` by default, and always `Secure` in production. Cookie name/domain/path/security values are environment-validated. CORS uses an explicit allow-list with credentials; wildcard origins are rejected.

Unsafe authenticated requests must carry an `Origin`, or a valid `Referer` fallback, whose origin is in the same explicit allow-list. This check complements `SameSite=Lax` and is covered by unit, integration and E2E tests. Login remains unauthenticated and is protected by a configurable per-client rate limit plus account lockout.

Changing a password revokes every other active session while preserving the current verified session. This lets first-login password change complete without issuing another token; the policy is covered by integration/E2E tests.

## Consequences

- No bearer token or session token is stored in browser storage.
- Database compromise does not directly reveal reusable session tokens.
- Deploy configuration must provide explicit trusted frontend origins and production-secure cookies.
- Non-browser clients must provide an approved Origin for unsafe authenticated operations.
- Capability authorization is intentionally outside this ADR and this work packet.
