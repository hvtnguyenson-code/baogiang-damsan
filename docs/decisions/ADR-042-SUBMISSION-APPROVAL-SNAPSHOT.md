# ADR-042 — Submission / Approval Snapshot

- **Status:** Accepted
- **Date:** 2026-08-23
- **Scope:** 05I0D architecture decision only; no implementation authorization.
- **Authority:** Product Owner D1–D19 recorded in `LOCAL-FC-05I0D-SUBMISSION-APPROVAL-SNAPSHOT-DECISION-CLOSURE.md`.

## Decision

V1 Reporting Statement is a **PERSONAL** immutable official-record revision, owned by one authenticated submitter. A logical series is `statementProfile + submitterUserId + academicYearId + fromCivilDate + toCivilDate`; `statementProfile` is a versioned business discriminator. UUID identifies one immutable revision in exactly one series. Series, revision UUID, semantic hash, and command idempotency identity are separate. Equal content/hashes may belong to distinct legitimate revisions and never establish uniqueness or current authority.

Scope is server-derived from historical date-effective `responsibleTeacher`, not client roots or `actualTeacher`. Current ReportingProjection is insufficient because it accepts explicit whole roots and does not derive personal scope, filter canonical detail by responsibility, or reaggregate. A separately closed Personal Reporting Projection/composition prerequisite is required before persistence. It must preserve ADR-041 canonical truth, filter PASS canonical detail for partial-root responsibility, recompute aggregates, preserve MAKEUP original-obligation ownership, and fail closed for every intersecting BLOCKED root. The Personal prerequisite now defines valid PASS ZERO_RESPONSIBILITY with zero counts/empty scope; V1 Statement submit accepts only RESPONSIBILITY_PRESENT PASS. ZERO_RESPONSIBILITY is ineligible before freeze/persistence and creates no zero-subject Statement; future policy requires explicit re-entry.

Official submission is only from a RESPONSIBILITY_PRESENT + PASS authoritative Personal projection and runs in one outer `SERIALIZABLE` transaction. It authenticates/authorizes, normalizes series and deterministic client command intent, then resolves command requestKey/fingerprint **before** new server semantic input. A same accepted command replays its authoritative prior revision/result and original frozen as-of without reporting or clock pin. Only a genuinely new command pins one server command-clock `asOfInstant`, enforces series guards, invokes the tx-aware resolver with exactly that instant, then validates, freezes, persists revision/lineage, writes history/audit, and commits. Fingerprint excludes pinned as-of, generated UUID/timestamps/token, audit/history IDs, and produced hash. Client cannot set official as-of; no later clock read changes new-command truth; stale/concurrency fails conflict, never mixed snapshot. Existing live/preflight API as-of semantics are unchanged.

A hybrid immutable snapshot plus provenance manifest is frozen. `REPORTING_STATEMENT_SNAPSHOT_V1` hashes canonical UTF-8-without-BOM JSON using SHA-256. It includes serializer/snapshot/profile versions, statementProfile, submitter/AcademicYear/range, pinned as-of, derived scope, canonical detail, aggregates, and ADR-041 provenance. It excludes UUID, lifecycle token, requestKey/fingerprint, audit/history IDs, timestamps, evaluatedAt, and persistence metadata. Distinct revisions may share hash only when every hashed field, including pinned as-of, is byte-semantically identical; hash is not identity, uniqueness, idempotency, or authority. Bytes have no insignificant whitespace, recursively sorted keys and accepted domain array order; instants are exactly `YYYY-MM-DDTHH:mm:ss.sssZ` UTC; civil dates are `YYYY-MM-DD`; schema-null is explicit null; schema-absent is absent; unexpected runtime undefined fails canonicalization; no secrets/incidental order/locale numbers. Serializer version owns future numeric compatibility.

Lifecycle is `SUBMITTED`, `APPROVED`, `REJECTED`, `SUPERSEDED`; no mutable draft/withdrawn/void. One series allows at most one unresolved SUBMITTED and one non-superseded APPROVED. Exact requestKey/fingerprint retries replay; another submit during unresolved SUBMITTED conflicts. Rejection/resubmission and approved correction create successor revisions. An approved predecessor stays current until successor approval; then successor APPROVED, predecessor SUPERSEDED, current-series authority, history and audit transition atomically. Database-backed/transactional enforcement and CAS are required later; semantic-hash uniqueness is forbidden.

Future submit uses `REPORTING_STATEMENT_SUBMIT` PERSONAL, server-normalized to submitter. Read uses `REPORTING_STATEMENT_READ`: owner PERSONAL, every frozen SUBJECT for non-owner, or same-key SCHOOL_WIDE. V1 creates no zero-subject Statement. If future policy permits one, SUBJECT-only non-owner access must fail closed rather than succeeding vacuously; owner PERSONAL and SCHOOL_WIDE remain governed normally. Existing `APPROVAL_PRINCIPAL` or `APPROVAL_VICE_PRINCIPAL` permits school-wide approve/reject. UUID self-approval/rejection is prohibited. No authority derives from role/title/membership/duty/assignment/SYSTEM_ADMIN/UI, and no CLASS or ACADEMIC_YEAR scope is introduced.

Domain history is immutable business provenance, proving revision/lineage/decision/supersession actors, request identity, lifecycle token and submission as-of. AuditEvent remains sanitized cross-cutting audit and never stores snapshot payload. Historical reads serve frozen evidence; no V1 physical deletion; current authority follows series lifecycle, never latest `createdAt` or mutable upstream heads.

## Consequences

Implementation order is Personal Reporting Projection prerequisite, persistence foundation, control plane, cross-domain E2E, Core Backend Freeze, then UI. Entry gates require tested ZERO_RESPONSIBILITY ineligibility; a future zero-subject policy must add fail-closed SUBJECT-read testing, tested responsibility handovers/partial-root aggregation/BLOCKED propagation, tx-aware resolver, server-pinned as-of/replay behavior, and later database-backed series/revision/CAS/idempotency/lineage/history invariants. Numeric limits, archival/retention, export, pagination, SLO, quorum and delegation defer.

This ADR preserves ADR-041 current-authoritative reporting and all PPCT/timetable/overlay/execution/progress-debt, MAKEUP, Special Activity, responsible/actual teacher, and BLOCKED semantics. It does not claim implementation exists.
